THE MESSAGE JOURNEY

Browser input. Linux transport. Verified delivery.

The browser provides the interface. Two separate C processes exchange the actual message using kernel-managed named pipes.

01Web interfaceSubmit a message
→
02Python bridgeForward to peer stdin
→
03C process Awrite() to FIFO
→
04C process Bread() and confirm

A receiving-process event returns through stdout to the bridge. The browser polls the bridge every 500 ms. Replies use the second FIFO in the opposite direction.

Why two pipes?

Each direction has its own channel: A → B and B → A. Both peers can send and receive. On Linux, each peer opens its FIFO descriptors with O_RDWR | O_NONBLOCK to avoid startup ordering deadlocks.

What counts as delivered?

A message is marked delivered only when the destination C process reports the matching message it read from the FIFO. Observed delivery time includes bridge scheduling and confirmation overhead; it is not a kernel-only benchmark.

Linux implementation

mkfifo()

Creates the two named pipes.

open()

Opens the peer's FIFO descriptors.

poll()

Waits for input without busy looping.

write() / read()

Transfers atomic JSON message frames.

close()

Releases FIFO file descriptors.

SIGTERM

Stops peers for restart or shutdown.

Session history retains the latest 500 messages and 200 transport events in memory. Export it before closing the server. Session counters include all messages submitted during the current server run.
